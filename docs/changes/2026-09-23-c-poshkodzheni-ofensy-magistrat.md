# 2026-09-23 — «напівнароджені» офенси після збою магістрату: поллер їх не бере, /process-one не палить AQL

## Контекст (сам збій — не в мідлварі)

14:25–18:11 на консолі qr-aio стояв персистер магістрату: отруєна durable MPC-транзакція
`0000559569.ser` (офенс Rule #105789 «Successful Login From a Compromised Host», attacker
`172.17.96.62` без address-id) зациклилась на recovery і заблокувала чергу з 374 транзакцій.
Рестарт `ecs-ep` не допоміг (файл переграється). Вилікувано карантином одного `.ser` з
`/store/mpc/core/tx_log` після бекапу; злив 476 → 2 файлів за 7 хв. Повний runbook — у
пам'яті (`qradar_magistrate_poison_tx_runbook`), бо це консоль, не репо.

## Що лишилось після фіксу

Усе, що кореляція **створила за ті 4 години**, лягло в API як OPEN з магнітудою й описом,
але з **`offense_source = null`** і без event-мапінгу — їхні detail-команди були в загубленій
транзакції. Заміряно о 18:45: **OPEN 4398, з них 1154 пошкоджених** (m5 784, m6 100, m7 10,
m4 109). За 40 хв після відновлення **жоден не «долічився»**.

Для мідлваря це виглядало як нова хвиля збоїв: поллер о 18:19 накинув 1304 «нових»
(черга 336 → 1503), воркер пішов їх обробляти — і **139 × HTTP 422** за пів години,
`ERROR 101`. Спокуса була списати на Ariel під навантаженням (load на консолі 22) — але
активних Ariel-пошуків було 0, а 422 = `FunctionCreateError` code 28523 зі `start_index`
рівно на `INOFFENSE(id)`: Ariel не може створити функцію для офенсу, якого немає в
event-мапінгу. Відтворено дослівно на #1448634 (`offense_source: None`).

Мідлвар при цьому поводився **правильно**: AQL не виконався → `close_on_empty` знято →
ERROR, офенс лишили OPEN, нічого не закрито наосліп. Проблема лише в марній роботі:
~1000 AQL у 422 зараз і повтор кожні 6 год через ERROR-requeue — вічно, бо самі вони не
лікуються.

## Що зроблено

- **`poller.py`**: у `fields` додано `offense_source`; офенс із `null`/порожнім джерелом
  **не кладеться в чергу** (крок 0, до матчингу) — лічильник «пошкоджені (source=null)» у
  підсумку рану. Це також не дає ERROR-requeue повертати їх щошість годин.
- **`app.py` `/process-one`**: якщо `entity_value` порожній — `skipped` **без AQL і без
  моделі**, `offenses.status = 'DAMAGED'`, офенс лишається OPEN. У черзі це `DONE`, а не
  `ERROR` → без повторів. `DAMAGED` ≠ `PROCESSED`, тож `is_processed_in_db` його не
  плутає з обробленим; `tools/catchup.py` його не ретраїть (RETRYABLE лише
  AQL_ERROR/NO_EVENTS).
- **Одноразово на mdlwr01**: пошкоджені прибрано з `work_queue` (QUEUED/ERROR) по списку
  id з API; список збережено в `/opt/qradar-middleware/damaged_offenses_20260923.txt`
  для рішення по самих офенсах.

## Що НЕ вирішено тут — рішення аналітика

1154 OPEN-офенси в QRadar, які **неможливо проаналізувати** (ні мідлваром, ні в UI —
INOFFENSE не працює), з них 10 × m7 і 100 × m6. Детект при цьому **не втрачено**: події в
Ariel цілі, правила перестворять здорові офенси на живій активності. Варіанти: масово
закрити як incident debris (Non-Issue, з нотаткою про причину) — або для m7/m6 руками
переглянути правило+вікно часу через AQL по логсорсу замість INOFFENSE. Автоматично цього
мідлвар не робить свідомо.

# 2026-08-28 (b) — Vertex лише на ескалації: повтор на tier-1 і видиме тіло помилки провайдера

## Контекст

Після фікса контексту на llm01 (запис -a) лишились два недоліки, через які дефект
провайдера три доби виглядав штатною роботою й коштував ~25 €/добу.

## Недолік 1 — тіло помилки провайдера не потрапляло в лог

`ask_openai` робить `response.raise_for_status()`, а `httpx.HTTPStatusError.__str__` дає
лише рядок статусу й URL. У журналі це виглядало так:

```
⚠️ Provider openai (qwen2.5-coder-3b) failed for offense 1264874:
   Server error '500 Internal Server Error' for url 'http://10.2.10.1:8080/v1/chat/completions'
```

Тобто «llm01 щось відповів 500» — і жодної підказки, що саме. Реальна причина
(`{"message":"Context size has been exceeded."}`) знайшлась лише коли запит відтворили
руками з mdlwr01.

**Зміна:** `describe_provider_error()` — рендерить виняток разом із тілом відповіді
(до 300 символів, схлопнуті пробіли) і типом винятку. Застосована в усіх чотирьох місцях,
де помилка провайдера пишеться в лог або повертається клієнту.

Перевірено на синтетичному `HTTPStatusError` у прод-venv:

```
БУЛО : Server error '500 Internal Server Error' for url 'http://10.2.10.1:8080/v1/chat/…
СТАЛО: HTTPStatusError: Server error '500 …' | відповідь: {"error":{"code":500,
        "message":"Context size has been exceeded.","type":"server_error"}}
```

## Недолік 2 — будь-яка відмова tier-1 одразу оплачувалась Vertex-ом

Стара логіка: один запит до `ai_provider`, і при будь-якому винятку — негайний
`ai_fallback`. Частина відмов транзитна (усі слоти llm01 зайняті сусідніми запитами
поллера), але кожна така дрібниця йшла в платний API.

**Зміна:** повтор на **тому ж** провайдері перед тим, як віддавати офенс кудись іще.
Нові ключі в `config_schema.py`:

| ключ | дефолт | що робить |
|---|---|---|
| `provider_retries` | 1 | скільки додаткових спроб на первинному провайдері |
| `provider_retry_delay_seconds` | 3 | пауза між спробами (дає слоту звільнитись) |

Невдала спроба пишеться окремим рядком `↻ … спроба N/M` з повним текстом помилки.

## Конфіг на проді: `ai_fallback` вимкнено

`ai_fallback: "vertex"` → `""`. Тепер Vertex задіюється **лише** там, де його й задумували:

- **ескалація** — `escalate_provider`, коли tier-1 дав `score > escalate_threshold` (0.6);
- **ручний глибокий аналіз** — `ai_manual_provider`, коли аналітик сам тригерить офенс.

Авто-тріаж, який не пройшов на llm01 після всіх спроб, більше **не** їде в хмару: офенс
отримує `AI_ERROR` і **лишається відкритим**. Це безпечно, бо `is_processed_in_db()` у
поллері рахує обробленим тільки статус `PROCESSED`, а нотатка в QRadar на цій гілці не
пишеться — тож наступний ран поллера (кожні ~10 хв) забере офенс знову.

Межа ризику: якщо llm01 ляже надовго, офенси накопичуються й через 48 год випадають із
вікна поллера. Тому llm01 під наглядом (`systemctl is-active`, `NRestarts`, VRAM,
помилки контексту/OOM, частка fallback >10%) — сесійний монітор із цієї ж роботи.

## Як відкотити

У `config.json` на mdlwr01 повернути `"ai_fallback": "vertex"`. Код при цьому не міняється:
гілка fallback лишилась на місці, вимкнена саме конфігом, як і задумано для host-специфічних
рішень.

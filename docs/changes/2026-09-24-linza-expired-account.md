# 2026-09-24 — лінза «Login failure to an expired account»: 221 офенс IT-гігієни закриваються самі

## Як знайшлося

Поверхневий аудит правил-генераторів офенсів (запит аналітика «підтюнити ті, що
створюють найбільше»). Серед типів, яких мідлвар **не бачить взагалі** (43% усіх OPEN —
1489 з 3453), четвертим за обсягом стояв **«Login failure to an expired account» — 221
відкритий офенс**, медіана віку 17 днів, **939 подій разом (~4 на офенс)**, усі з
`Server_Network`/внутрішніх джерел, усі — іменовані співробітники.

## Що це насправді

Правило **#118289 `Login Failure to Expired Account`** (OVERRIDE стокового #100059) фаєрить на
**одну** подію Windows 4625 sub-status *Expired Password* (`An account failed to log on:
Expired Password`). Реальна картина в подіях: користувач із простроченим AD-паролем
логіниться на власну машину (`Src 127.0.0.1`, logon type 2) або проходить через
mfaa `172.17.61.173` / DC (`.112`, `.6`, `.252`, logon type 3). Це password-expiry-гігієна
для helpdesk, не безпека. Але в цьому ж потоці є два сигнали, які варто бачити:
прострочену креду **пробують знадвору** (хтось поза мережею має старий пароль
співробітника — витік/reuse), і **адмін/сервісний акаунт** із простроченим паролем
(ops-проблема, що ламає сервіси).

## Що зроблено

- **`queries/expired_account.aql`** — бенін-префільтр: віддає рядки лише якщо `Src`
  зовнішній (не RFC1918, не loopback) **або** `Acct` схожий на admin/service/machine
  (`adm*`, `*admin*`, `svc*`, `sa`, `*$`). Іменований юзер із внутрішнього/loopback
  джерела → 0 рядків.
- **`prompts/expired_account.md`** — FIRST CHECK на зовнішній `Src` (0.7, лишається
  OPEN; наші власні публічні egress → 0.3), service-account (0.4, авто-закриття з
  іменем акаунта в поясненні), стеля 0.8 (прострочений пароль не може успішно
  спрацювати — «компрометації» тут бути не може).
- **`prompts.json`**: ключ `Login failure to an expired account` → `close_on_empty`,
  поставлений **передостаннім** (перед `Default`), щоб на композитах вигравали сильніші
  лінзи.
- Накопичені 221 OPEN — за межами 48-год вікна поллера → прогнано `tools/catchup.py
  --offenses <ids>`: кожен пройшов через чергу, AQL порожній → `close_on_empty` 0.0 з
  нотаткою `AUTO-CLOSE`.

## Чого не робили

Не чіпали саме правило #118289 (можна було підняти поріг з 1 події або зняти в report).
Лінза дешевша й дає більше: не «менше офенсів», а «офенси є, і ті кілька, що мають
сенс (external / service account), доходять до аналітика, решта закривається без моделі».
Ціна дренажу — лише AQL по одному-чотирьом подіям.

Решта Вісі 1 (IRC Connections 512 → виключити GUEST/LAN_WIFI; Suspicious Web Server
Activities 307 → вимагати успішну відповідь; Same User Logins to Multiple Devices 130 →
виключити RDS-хости) — це правки тестів правил, які API не міняє; передано аналітику
з точними id (#119894, #128694, #146244).

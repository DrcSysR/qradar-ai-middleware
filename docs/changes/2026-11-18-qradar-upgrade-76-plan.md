# 2026-11-18 — План оновлення QRadar 7.5.0 UP14 → 7.6.0.x

**Статус: ПЛАН, не виконано.** Виконує людина (адмін QRadar + VMware); цей документ — послідовність і критерії.
Джерела: release notes IBM (UP16, SFS 7.6.0, 7.6.0 FP5, lifecycle), публікації спільноти. Сторінка SFS 7.6.0 віддавала
HTTP 403 — її зміст береться зі зведень пошуку, тож **перед вікном звірити з Fix Central** (див. «Відкриті питання»).
Upgrade Guide PDF для 7.6 (`b_qradar_upgrade.pdf`) на момент перевірки описував оновлення до 7.5.0 UP8 — не покладатись на нього.

## 1. Цільовий маршрут

`7.5.0 UP14` → *(за потреби)* `7.5.0 UP15` → `7.6.0` (≥ **7.6.0.1**, мінімальна рекомендована ціль IBM) → `7.6.0 FP5` або новіший (FP6 вже є).

- **UP16 не ставити** — він блокує пряме оновлення на будь-який 7.6.0 і fix pack.
- Зведення пошуку про SFS 7.6.0 перелічують джерела: UP11 IF01–04, UP12 (+IF01–03), **UP14 IF01–IF05**, UP15 (+IF01–04). Голого UP14 без IF у переліку немає.
  На консолі interim-фіксів не знайдено (`rpm -qa | grep -i interim` порожній) → або (a) підтвердити на Fix Central/в release notes, що UP14 без IF підтримується,
  або (b) спершу піднятись до UP15 (окремий етап A). **До підтвердження планувати етап A.**
- FP5 ставиться з 7.6.0 FP1–FP4 і виправляє DT500809 (деградація rule engine після 7.6.0.1) — у нас 606 правил, тож **7.6.0 і FP — одне вікно або дві доби поспіль**, не залишати систему на голому 7.6.0.1.
- Між етапами — витримка 24–48 год (спостереження за EPS, офенсами, застосунками).

## 2. Підготовка (T-14 … T-1)

1. **Рішення про вікно:** бажано вихідні/ніч; QRadar під час оновлення недоступний, події UDP-джерел (syslog від WLC/PA/Cisco) **втрачаються**, TCP-джерела й `api-gw`-релей накопичують у чергах. Оцінити тривалість: IBM цифр для 7.6 не дає; для консолі з 2,4 ТБ даних закласти 4–8 год на етап (оцінка, не вимір) + запас.
2. **Підтвердити маршрут** (відкритe питання 1) і скачати SFS з Fix Central під обліковий запис IBM: UP15 (якщо етап A), 7.6.0, FP5/FP6. Для кожного — `sha256sum` проти значення на Fix Central і перевірка підпису утилітою code signing 1.0.2 (за release notes).
3. **Бекапи:**
   - увімкнути/запустити конфіг-бекап (Admin → Backup and Recovery → On demand configuration backup) і **забрати копію з `/store/backup` за межі хоста** (зараз каталог порожній);
   - **знімок VMware** `qr-aio` і `qr-uph` безпосередньо перед стартом (без пам'яті, quiesce за можливістю). Диск `/store` 2,9 ТБ — узгодити з адміном VMware місце під дельту й видалити знімок після витримки (довго живий знімок деградує I/O). Це **єдиний підтримуваний відкат** патча QRadar;
   - `cp -a /etc/sysconfig/network-scripts /root/ifcfg-backup-$(date +%F)` і `ip -d link; ip r` у файл — для порівняння після переходу на NetworkManager.
4. **Деплой змін:** Admin → Advanced → Deploy Full Configuration не потрібен, але **«Deploy Changes» має бути без очікуючих змін** (інакше інсталятор відмовить).
5. **Місце:** `df -h /storetmp /var/log` на обох хостах (≥10 ГБ у `/storetmp`; зараз 12 ГБ — мало запасу, якщо там лежить інше: `ls -la /storetmp`). SFS не лишати в `/storetmp` без оновлення — нічний `diskmaintd.pl` його видалить.
6. **Мережа/фаєрвол:** дозволити Auto Update на `au.ibm.qradar.com` (лише FQDN, без статичного IP; після оновлення перевірити, що URL закінчується `/`). Сторонні системи, що очікують фізичний IP хоста з застосунками — у нас HA немає, не актуально.
7. **WinCollect:** якщо є керовані агенти WinCollect 7 — потрібен 7.3.1 Patch 4 (перевірити Admin → Data Sources → WinCollect).
8. **Застосунки:** зафіксовано 19; після оновлення вони перебудовуються/перезапускаються. Оцінити, чи потрібні `QRadar GraphQL` і `Analyst Workflow` (STOPPED) — не оживляти заради оновлення. Для `CrowdStrike Falcon *` та `Google SCC` перевірити на IBM App Exchange сумісність із 7.6 (відкрите питання 3).
9. **Мідлвар:** за 1 год до вікна на mdlwr01 — `systemctl stop qradar-poller.timer qradar-worker.timer` (poller/worker і так вміють `QRADAR_UNAVAILABLE`, але зайві запити під час міграції ні до чого); `cortex_xdr_scan` не залежить від QRadar. Автоперезапуск `qradar-middleware.service` лишити.
10. **Базовий знімок:** `ssh mdlwr01 'cd /opt/qradar-middleware && venv/bin/python tools/qradar_upgrade_check.py snapshot upgrade_baseline_pre_<дата>.json'` — повторити за годину до вікна (потік подій, офенси, статуси).
11. **Попередити** користувачів QRadar/аналітиків і власників джерел про недоступність і про можливі прогалини в UDP-подіях.

## 3. Етап A (за потреби): UP14 → UP15

За release notes SFS (команди — стандартна процедура QRadar SFS; звірити з release notes конкретного файлу):

1. Консоль `qr-aio`: SSH під root, `screen -S upgrade` (сесія не має обриватись).
2. Скопіювати SFS у `/storetmp`; `sha256sum` — звірити.
3. `mkdir -p /media/updates && mount -o loop -t squashfs /storetmp/<файл>.sfs /media/updates && /media/updates/installer`
4. У меню інсталятора — **Patch Console**, дочекатись завершення (HTTP-сесії закрито, не втручатись). Керовані хости (у нас лише App Host) оновлює консоль.
5. `qr-uph` окремо не оновлюємо: консоль доставляє патч на App Host сама (за уточненням власника); лише переконатись, що він прийняв патч — `myver -v` на `qr-uph` і статус хоста в Admin → System and License Management.
6. `umount /media/updates`; `/opt/qradar/bin/myver -v`; видалити SFS.
7. **Перевірки (розділ 6)**; витримка 24–48 год.

## 4. Етап B: 7.6.0.x

1. Той самий порядок, що в етапі A, SFS 7.6.0. Попередньо ще раз: усі апарати на одній версії з консоллю, deployed без змін, місце на місці.
2. Після інсталятора перезавантаження хоста можливе — не переривати.
3. Очікувати міграції/перебудови (застосунки, конфіг мережі → NetworkManager). Спостерігати `/var/log/setup-*/patches.log` і лог інсталятора.
4. **Одразу перейти до етапу C** (рекомендовано в ту саму добу), щоб не жити на 7.6.0.1 з DT500809.

## 5. Етап C: 7.6.0 FP5 (або новіший)

SFS fix pack'у (потрібно ≥5 ГБ у `/storetmp`), та сама процедура. Перевірки розділу 6; після — витримка 48 год.

## 6. Перевірки після кожного етапу

1. `ssh qradar '/opt/qradar/bin/myver -v'` і `curl -k -H "SEC: …" …/api/system/about` — очікувана версія.
2. **Знімок і порівняння:** `venv/bin/python tools/qradar_upgrade_check.py snapshot post_<етап>.json && venv/bin/python tools/qradar_upgrade_check.py diff upgrade_baseline_pre_20261118.json post_<етап>.json`. Червоні прапорці: застосунок не RUNNING, більше log source'ів у `ERROR` (база: 918), потік подій упав >30% (база ≈937 тис./15 хв).
3. **Мережа консолі (7.6):** `nmcli con show; ip -br a; ip r` — ens192 має адресу/шлюз як до оновлення (порівняти з `/root/ifcfg-backup-*`). Не редагувати bond (DT472949).
4. **Потік подій:** Log Activity — свіжі події від ключових джерел: `PaSeries`, `WindowsAuthServer`, NPS (xdc02/xdc05), Sysmon, `Bind @ 172.17.61.157`, nginx2, Zimbra, Cortex XDR (через `api-gw`); правило «Log source stopped sending» не спрацьовує масово.
5. **Правила й офенси:** кількість увімкнених правил 606; нові офенси з'являються; перевірити продуктивність rule engine (Admin → System and License Management → Performance / затримка подій у Log Activity) — ознака DT500809.
6. **Мідлвар (після запуску таймерів):**
   - `ssh mdlwr01 'cd /opt/qradar-middleware && python3 tests/smoke_test.py'`;
   - `GET /api/system/about`, `/api/siem/offenses?filter=status="OPEN"&fields=id` з `Version: 19.0` (якщо версію API знято з підтримки — оновити заголовок);
   - тестовий AQL із `tools/aql_runner.py` (синтаксис `LIMIT n START … STOP …`, `UTF8(payload)`, `LOGSOURCENAME`, `INOFFENSE`) — порівняти результат із відомим офенсом;
   - `systemctl start qradar-poller.timer qradar-worker.timer`; через 10–20 хв — `queue_db` глибина, `poller.log` без `QRADAR_UNAVAILABLE`;
   - **custom actions на qr-aio** (9 скриптів → PA User-ID) і playbook-и: ручний тест одного (`push-ip.sh`-подібний шлях) — скрипти лежать на qr-aio й могли бути зачеплені оновленням ОС;
   - Cortex: наступний звіт 09:30 приходить.
7. **Застосунки:** Admin → Apps — усі RUNNING, крім двох свідомо зупинених; оновити застосунки, що просить App Framework.
8. **Auto Update:** Admin → Auto Update → Settings, Get new updates; після 7.6 — оновити DSM/protocol/QID-пакети. Якщо ставляться — перевірити, що наші custom parsing (positional hostname для `api-gw`) не зламано: подивитись, що `Bind`, `nginx`, `CortexXDRCustom_ext` лишаються у своїх log source'ах, а не падають у `SIM Generic`.
9. **MaxMind** (геоAQL/прапорці Log Activity) — оновити; очистити кеш браузера.

## 7. Критерії відкату

| Ситуація | Дія |
|---|---|
| Інсталятор впав / хост не завантажується | Не повторювати наосліп: логи, звернення в IBM Support; за потреби **відкат знімком VMware** |
| Після етапу немає потоку подій / консоль недоступна >1 год понад заплановане | Відкат знімком (на обох хостах разом — версії мають збігатись) |
| Деградація rule engine (затримки подій ростуть, DT500809) | Спершу FP5/новіший, не відкат |
| Збій окремого застосунку | Перевстановити/оновити застосунок, не відкат |

QRadar не має підтримуваного «unpatch». Відкат = знімок VMware + втрата подій за час між знімком і відкатом (UDP) / повторна доставка TCP-черг. Знімок видалити лише після витримки (≥48 год на фінальній версії).

## 8. Відкриті питання (закрити до вікна)

1. **Чи приймає SFS 7.6.0 голий UP14 (без IF)?** Прочитати «supported versions» у release notes SFS на Fix Central (мені відповіло 403). Якщо ні → етап A (UP15) обов'язковий.
2. **Чи переходить 7.6 на RHEL 9** і чи потрібна міграція ОС — у зібраних джерелах не підтверджено; IBM лише пов'язує перехід на NetworkManager з дорожньою картою RHEL 9/10. Прочитати «What's new in 7.6.0».
3. **Сумісність застосунків** (CrowdStrike Falcon Intel/EndPoint, Google SCC, SOAR Plugin, Advisor with Watson) із 7.6 — IBM App Exchange.
4. **Чому `/store/backup` порожній** і чи є зовнішнє резервування конфігурації QRadar; якщо ні — це самостійна дрібниця для виправлення незалежно від оновлення.
5. **Чому 918 із 1733 log source'ів у статусі `ERROR`** (існуючий стан) — розібрати до оновлення, інакше після нього не відрізнити старе від нового. Багато з них можуть бути незадіяними/застарілими записами; чистка зменшить шум порівняння.
6. **Тривалість міграції БД** на 7.6 — у джерелах не наведена; для 7.5.0 FP1+ IBM попереджала про «багато годин». Узгодити вікно з запасом.

## 9. Інструмент

`tools/qradar_upgrade_check.py` (лише читання): `snapshot [файл]` і `diff до після`. Запуск із mdlwr01 через `venv/bin/python`.

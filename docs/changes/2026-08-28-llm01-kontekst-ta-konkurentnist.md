# 2026-08-28 — llm01: спільний KV-кеш зʼїдав tier-1 (83% відмов), конкурентність поллера

## Контекст

Задача звучала як «підняти `poller_concurrency` і воркери gunicorn». Замір перед зміною
показав, що обидва ці важелі — не вузьке місце, а справжня причина була на llm01.

## Крок 1 — підняття конкурентності не дало нічого

`poller_concurrency` у `config.json` не був заданий узагалі (дефолт 3) → виставлено 5,
воркери gunicorn 3 → 4.

Результат заміру:

```
конкурентність 3:  07:54 → 08:16   100 офенсів   22.5 хв
конкурентність 3:  08:17 → 08:29   100 офенсів   12.1 хв
конкурентність 5:  08:30 → 08:44   100 офенсів   13.9 хв
```

Тривалість рану гуляє 12–22.5 хв ще ДО зміни, тож єдина точка на конкурентності 5 лягає
всередину наявного розкиду — покращення нема. Натомість частка відмов llm01 підскочила
з ~50% до 92%. `poller_concurrency` повернуто на **3**; воркери gunicorn лишені на **4**
(нешкідливо, RAM вистачає).

Ресурси mdlwr01, які пояснюють, чому воркери тут ні до чого: **2 vCPU, 2 ГБ RAM**.
Load average 2.3 виглядає як насичення, але миттєвий зріз дає ~60% idle і сплески iowait,
а процеси показують 0% CPU — навантаження тримають процеси в D-стані на мережевому IO.

## Крок 2 — справжня причина: `kv_unified` на llm01

`llama-server` був запущений так:

```
llama-server --model qwen2.5-coder-3b-instruct-q4_k_m.gguf --n-gpu-layers 24 \
             --ctx-size 8192 --threads 8 --host 10.2.10.1 --port 8080
```

`--parallel` не заданий, тож білд підняв 4 слоти за замовчуванням:

```
srv load_model: initializing, n_slots = 4, n_ctx_slot = 8192, kv_unified = 'true'
srv decode: failed to find free space in the KV cache, retrying with smaller batch size...
```

При `kv_unified = true` чотири слоти ділять **один спільний KV-кеш на 8192 токени**, хоча
кожен слот рапортує собі 8192. Два одночасні запити по ~4000 токенів уже не вміщаються.
Звідси плаваюча межа: бісекція під навантаженням поллера показала, що реально влазить лише
**~550 токенів промпта**, при тому що `/props` рапортує 8192.

Мідлваре будує промпти під бюджет 8192, тож більшість запитів відбивалась з
`500 {"message":"Context size has been exceeded."}` і йшла у fallback на Vertex.

## Зміна

`/etc/systemd/system/llama-server.service` на llm01 (бекап —
`/root/llama-server.service.bak-20260828`):

```diff
-  --ctx-size 8192 \
+  --ctx-size 24576 --parallel 3 \
```

Кількість слотів зрівняна з `poller_concurrency` 3, а `--ctx-size` = 3 × 8192, тож кожен
слот отримує повний контекст. Після рестарту llama.cpp сам перемкнувся на роздільний кеш:

```
srv load_model: initializing, n_slots = 3, n_ctx_slot = 8192, kv_unified = 'false'
```

## Ризик, який лишається

VRAM на Quadro P620: **1963 з 2048 МіБ зайнято, вільно 30 МіБ**. KV-кеш виділяється при
старті й під навантаженням не росте, тож стан стабільний — але запасу нема. Якщо на цю GPU
зайде щось іще, або знадобиться більша модель чи більший контекст, треба зменшувати
`--n-gpu-layers` (частина шарів піде в RAM, там 24 ГБ вільно; ціна — швидкість генерації,
зараз ~198 ток/с на prompt-eval і ~11 ток/с на генерацію).
